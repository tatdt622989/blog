Jev 1.14 更新整理：圖片輸入、Box 定位與 262k 長上下文

Jev 1.14.0 在 2026 年 10 月 14 日推出。這次 TypeSafe AI 除了更新模型，也開放圖片輸入、Box 位置定位，以及更長的上下文。原本專注文字判斷的決策介面，開始能接進視覺工作流。

如果你第一次聽到 Jev，可以先讀前一篇 Jev 是什麼？System One 模型與機率決策入門，了解 Choice、Score、Noul 的用途。這篇接著整理新版本的變化，資料查核至 2026 年 10 月 17 日；內容依據官方公告與文件，未執行付費 API 評測。

先確認版本：jev-latest 還不等於 1.14

截至查核日，官方模型文件 的對應如下：

呼叫時填入的名稱 目前對應版本
jev-latest jev-1.13.0
jev-preview jev-1.14.0
jev-1.14.0 明確指定 1.14.0

想重現新版行為，我會直接填固定版本。否則程式碼沒改，別名更新後結果也可能跟著變動。兩版目前都維持 每百萬輸入 token 0.042 美元，輸出免費。

1.14 官方公告 將多語言支援列為預期改善最大的部分，也預告一週後更新 jev-latest。這是後續切換計畫，不能當成今天已完成；中文任務的改善幅度仍要用自己的資料驗證。

圖片能放進輸入，也能成為判斷標準

圖片文件 說明，圖片可以放進 state、instructions、criteria。例如整理商品照片時，輸入待分類圖片，再把不同分類的參考圖放進判斷標準，讓問題更具體。

這次也替 1.13 開放圖片能力。真正要留意的是：圖片仍屬於 Danger Zone 實驗功能，需要在請求標頭加入 TypeSafe-Danger-Zone-Images: true。它適合先做原型，官方尚未將可靠度列為正式生產標準。

我的看法是，先從一種範圍小、定義清楚的視覺判斷開始，會更容易找到問題。

Box 新增位置輸出，但找不到物件也會回傳框

新增的 Box 只支援 1.14，用來回傳單一物件的邊界框。top、bottom、left、right 都是 0 到 1 的相對座標，分別對應圖片高度或寬度。官方 Box 文件 有完整格式。

這裡有個容易踩到的坑：Box 沒有「找不到」的答案，目標不存在時仍會回傳一個框。 因此可以在同一次請求加問 Noul「目標是否存在」，由程式決定要不要採用座標。

下面是依 HTTP 圖片上傳格式 撰寫的介面範例，未執行實測。先準備自己的 product.jpg，並在環境變數設定 TYPESAFE_API_KEY；真正執行會使用帳號額度。

不要只看到有座標就執行後續動作。我會把「目標不存在、畫面模糊、同時有多個杯子」都放進測試資料。

長上下文開到 262k，仍要控制輸入範圍

依 上下文限制文件，預設是整個請求 64k、單一問題 32k；加入 TypeSafe-Danger-Zone-Long-Context: true 後，兩個上限都可提高到 262k token，1.13 與 1.14 都能使用。

這項能力同樣需要主動開啟。官方提醒，長上下文會更慢、準確度也會降低。以客服分類為例，我仍會先取出與當前問題相關的紀錄，再決定是否需要放大上下文。

SDK 也更新了，JavaScript 專案先看 Node.js 版本

這次不能只看模型名稱，套件環境也有變化：

  • Python SDK 0.7.5 加入圖片資產與 Box 支援，並預設啟用 zstd 請求壓縮。
  • JavaScript SDK 0.7.0 加入圖片與 Box，同時將最低執行環境提高到 Node.js 22，並停止匯出請求 payload 型別。

如果服務仍用 Node.js 18 或 20，我會分別驗證環境升級與模型切換。出了問題時，也比較容易找出原因。

真實案例值得參考，成本數字要看適用範圍

TypeSafe 10 月 7 日發布的 Jack & Jill 案例 提到，候選人初篩流程每千人的成本由 0.755 美元降到 0.092 美元。這是廠商發布的特定客戶案例，不能直接推算成任何專案都能省下相同比例。

這個案例讓我想到，可以先挑出一個量大、輸出固定的判斷步驟。再比較成本與品質，決定是否擴大使用。

導入前，先把判斷錯誤和格式錯誤分清楚

即使輸出符合型別，內容仍可能判斷錯。System One 文件 也說明，機率校準不保證每個答案都正確。前篇提到的「零幻覺」，應聚焦理解為輸出受型別與選項約束，不能延伸成業務判斷永遠正確。

另外，目前的 Confidence 文件 明確區分：Choice、Score 有 confidence，Noul 直接提供是非機率，沒有獨立的 confidence 欄位。接續前篇範例實作時，請以現在的官方回應格式為準。

我會先保留舊版當比較基準，用同一批資料檢查新版的錯分、漏判、延遲與費用，再調整自動處理的門檻。圖片、Box 與長上下文則各自測試，通過後才加入原有流程。

若還在思考 Jev 該放進系統的哪個位置，接著讀 Jev 入門介紹：三種決策原語、五大應用場景與開源工具鏈。先選好模型負責的判斷，再挑需要的新功能，成果也更容易驗證。
